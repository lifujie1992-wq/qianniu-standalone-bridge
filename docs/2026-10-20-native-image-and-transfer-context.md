# 原生图片及转接历史读取

1.6.19 的图片回查依赖网页 `_db.msgDataMap`，转接历史也依赖聊天网页缓存。
真实 9.97.86N 接待使用原生界面，连接的 dx-h5 页面没有这些对象，因而上述
逻辑即使单元测试通过，在该电脑仍无法取得原图和转接前的问题。

## 读取路径

`native_message_store.js` 观察当前千牛进程已经打开的 `sqlite3.dll` 查询连接，
只使用该连接的 `libaim/<当前登录 UID>@cntaobao/database/im.sqlite` 消息表。
通过 AppBiz 服务的店铺账号与 UID 严格匹配连接；只暴露固定的只读消息查询，
参数绑定，不接收 SQL。不读取数据库密钥，不打开或改写千牛数据库文件，
不调用 GetNewMsg/历史游标接口，不向买家发送消息。

连接及分片缓存不跨进程保存，关闭连接时失效；读取与关闭通过连接锁协调。
已缓存语句通过临时 step
观察取得连接，取得后解除该临时观察。读取结果有行数、字节及结构层数限制。

`native_context.py` 解码 AIM 的 MessagePack 文本及图片正文。完整 ccode、原始
消息 ID、创建时间和发送者身份必须匹配；撤回、删除、其他店铺人员及未知
格式不进入上下文。图片只用同消息原始正文中的 URL；保留消息说明文字。
原生库不可用时，保留原来的浏览器图片回查兜底。

## 上报顺序

原始消息先落本地持久队列，在上报工作线程中补图及读取转接历史。只对转给
当前客服的转接消息补其当日、转接时刻之前的最多 100 条历史。窗口以该
转接 ID 在原生库中的平台时间为准，避免用延迟收到通知的日期截断上文。历史标记
`capture_mode=history_snapshot`，与实时转接分开，在同一有序上报链路先传历史。
每批不超过 100 条；跨批必须先取得历史的持久化 ACK，再传实时转接。
历史不启动草稿轮询。原有 buyer_id、msg_id、ts 和其他实时字段不重写。

本地补传记录仅补显示及图片字段，保留已有消息的实时类型和投递状态，不把
已有消息重新排入实时回复队列。
历史客服消息采用服务端认可的 `role=mall_cs`，同时带实际观察到的发送者 UID、
昵称和接收者昵称；同店其他席位也按客服身份记录。本地仅允许同账号、同买家、
同消息 ID 的原生历史记录修正角色证据，不重分类实时消息。

## 验证边界

- 在真实 9.97.86N 登录进程，已读取目标会话转接前 10 条实际消息，原始 ID、
  身份和时间完整；一轮读取约 3 ms。
- 已按确切消息 ID 从原始正文取到图片地址，并下载到 139570 字节的有效图像。
- 已增加身份隔离、撤回/删除、MessagePack 边界、图片精确匹配、历史顺序及
  ACK 门槛回归。
- 最终隔离回归 391 项：390 通过、1 项因源码不含完整打包运行库跳过；
  实际消息经过读取、解码及本地模拟 ACK 上报组包也已验证。
- 经用户明确授权，10 条历史及 1 条图片上下文已取得真实大脑持久化 ACK，
  服务端会话可读到全部 11 条记录；此次历史补传没有新增 AI 回复。
- 补传验收发现旧 `seller` 角色被服务端回落为买家，已在客户端改为 `mall_cs`。
  同 ID 重传只返回 duplicate，未修正服务端既有的 3 条错误角色记录，需服务端
  按原 ID 定点修复；不能通过换 ID 重放或触发真实买家回复来修复。
- 相同图片在隔离模拟会话按完整图片事件上报后，大脑仍返回
  `image_handoff / buyer_image_needs_human`，模型原文表示图片未加载。
  原图可取得不等于模型已经看见图片；服务端图片下载、格式处理、视觉模型选择
  及多模态请求构建尚未验证，识图不视为通过，不发布为完整修复安装包。
